# ZCD vs. 三种备选方案的对比

> 本文回答"为什么是 overlay on dsh"，以及"如果换一种做法，代价是什么"。
> 结论用在评审会上，不需要读完所有细节文档。

---

## 1. 四个方案

| 方案 | 一句话 | 上游同步 | 首次成本 | 长期成本 |
|---|---|---|---|---|
| **A. Overlay on dsh（推荐）** | dsh 只读，产品差异在 bundle/插件/patch | 易（重放 patch + 测试） | 中 | 低 |
| B. Fork dsh | 复制源码，自由改 core | 难（手工合并） | 中 | 高 |
| C. ZCode 插件化改造 | 在 ZCode 上加 Cordis 式扩展 | 不适用 | 极高 | 极高 |
| D. 双写集成 | 两个产品并存，靠协议互通 | 不适用 | 高 | 高 |

---

## 2. 逐项对比

### 2.1 首次成本

| 工作 | A | B | C |
|---|---|---|---|
| 骨架/构建 | 2–3 周（复刻 client bundle） | 1 周（直接改） | 8–12 周（拆 runtime） |
| 工具语义 | 10–14 周 | 10–14 周 | 10–14 周（还要改 ZCode 的工具体系） |
| 工作流 | 20–25 周 | 20–25 周 | 20–25 周（但需绕过 ZCode 的单例注册表） |
| UI | 10–14 周 | 10–14 周 | 0（ZCode 已有） |
| 合计 | **56–75 周** | 51–68 周 | **68–95 周** |

> B 的首发略快，因为它省掉 overlay 的适配；但 C 反而更慢——ZCode 的 `AgentRuntime`、`ToolRegistryImpl`、`packages/services` 与 Electron 强耦合，插件化不是"加接口"而是"重写装配"。

### 2.2 长期成本（以 12 个月、每两周一次上游同步计）

| 方案 | 每次同步 | 12 个月累计 | 风险 |
|---|---|---|---|
| A | 0.5–1 人日（重放 patch + 测试） | 13–26 人日 | 上游 breaking 可控 |
| B | 2–5 人日（手工合并冲突） | 52–130 人日 | 冲突累积，最终可能停止同步 |
| C | 不适用（ZCode 无同步概念，但每次上游功能都要手工搬） | 高 | 双份维护 |
| D | 每个功能都要做两遍 | 最高 | 语义漂移 |

**这是决定性因素**：B 的首次优势（5 周）会在 3–4 个月内被同步成本吃掉。

### 2.3 能力可达性

| 能力 | A | B | C |
|---|---|---|---|
| 替换 agent loop / tool registry / session store | 可以（seam） | 可以（改源码） | 不可以（单例） |
| 新增 seam（durable workflow） | 可以 | 可以 | 可以，但要改 ZCode 的 runtime 装配 |
| 复用 dsh 的 sandbox/approval/guard | 直接 | 直接（但可能被改坏） | 没有 |
| 复用 ZCode 的成品 UI | 需要重做 | 需要重做 | 直接 |
| 复用 ZCode 的产品面（bots/share/mobile） | 不做 | 不做 | 直接 |

> C 的唯一优势是"UI 与产品面现成"，但我们的第一版明确不做产品面（`10-roadmap.md` §9），所以这个优势用不上。

### 2.4 安全与合规

| 维度 | A | B |
|---|---|---|
| 安全不变量（沙箱/guard/审批） | 继承 dsh，不被改动 | 改 core 时容易破坏；需要额外回归 |
| 审计（事件溯源/回放） | 继承 dsh | 改 core 后 replay 可能失效 |
| 许可 | 不复制 ZCode 代码；技能带 NOTICE | 同，但 fork 后更容易"顺手复制" |
| 上游安全修复 | 随 pin 版本获得 | 需要手工合并 |

---

## 3. 什么时候该改选

| 触发条件 | 建议 |
|---|---|
| 连续 3 个能力必须改上游 core | 重新评估 B（或把改动 PR 回上游） |
| `overlay/` 文件 > 10 或单 patch > 200 行 | 评估 B |
| 上游 6 个月无 release / 停止维护 | 评估 B（冻结 fork） |
| 必须复用 ZCode 的成品 UI 与产品面 | 评估 C 或 D |
| 必须支持 ZCode 的 Workspace 插件 scope | 先看能否用 dsh preset 表达；不能则 B |

---

## 4. 我的判断

1. **A 是唯一"可持续"的方案**：它把"产品差异"放在数据层（patch），把"能力"放在插件层，把"内核"留给上游。
2. **B 的诱惑是"改起来爽"**，但代价在 3 个月后出现；除非你打算长期脱离上游，否则不建议。
3. **C 看起来"复用最多"**，实际上要重写 ZCode 的装配层，且拿不到 dsh 的沙箱/guard/事件溯源——这三样恰好是我们最想要的。
4. **D 只在"两个产品都要上线"时才合理**，与当前目标不符。

> 一句话：**A 把复杂度放在"设计 seam"上，B 把复杂度放在"合并冲突"上，C 把复杂度放在"重写"上。** 选 A。
